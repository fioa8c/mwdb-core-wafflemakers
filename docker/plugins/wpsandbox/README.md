# wpsandbox — MWDB plugin

Adds a "WP Sandbox" tab to the sample page. A run executes the sample inside a disposable
SecEx WordPress microVM and attaches a behaviour report (`TextBlob`, `blob_type="wp-sandbox-report"`)
plus attributes `c2_host`, `dropped_file`, `wp_user_added` to the sample.

Spec: `docs/superpowers/specs/2026-08-27-wpsandbox-plugin-design.md`.
Components: this plugin (API + tab), `docker/wpsandbox-worker/` (executes runs), `docker/wpsandbox-template/` (SecEx template + harness).

## API

| Method | Path | Notes |
|---|---|---|
| `POST` | `/api/wpsandbox/<hash>` | body `{mode, path?, method?, query?, body?, timeout?}` → `202 {run_id}`; needs `adding_blobs` |
| `GET` | `/api/wpsandbox/<hash>` | `{runs: [...]}` newest first |
| `GET` | `/api/wpsandbox/run/<id>` | poll |
| `PATCH` | `/api/wpsandbox/run/<id>` | worker only |
| `DELETE` | `/api/wpsandbox/run/<id>` | cancel while `queued` |

## Schema

The `wpsandbox_run` table is created by the plugin itself at startup
(`WpSandboxRun.__table__.create(bind=db.engine, checkfirst=True)` in `model.py`),
**not** by an Alembic migration. Because `WpSandboxRun` subclasses `db.Model`, the
table is nonetheless registered in MWDB core's `db.metadata` for as long as the
plugin is loaded. That means `flask db migrate` run with the plugin enabled will
try to add `wpsandbox_run` to a new core migration, and run with the plugin
disabled (or absent) will instead emit `op.drop_table("wpsandbox_run")`. Anyone
regenerating core Alembic migrations must manually strip any `wpsandbox_run`
`create_table`/`drop_table`/index operations from the autogenerated revision
before committing it.

Attribute definitions (`c2_host`, `dropped_file`, `wp_user_added`) are created
automatically by `attributes.ensure_attribute_definitions()`, but no
`AttributePermission` rows are — granting `read`/`set` on these keys to the
relevant groups is a manual deployment step.
